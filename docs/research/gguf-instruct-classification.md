# Classifying a GGUF artifact as instruct/chat from its headers

Research for [#13](https://github.com/QuaanNguyen/q.it/issues/13) (part of [#8](https://github.com/QuaanNguyen/q.it/issues/8), blocks [#21](https://github.com/QuaanNguyen/q.it/issues/21)).

Sources are pinned to upstream commits so line links stay stable:

- llama.cpp `b81c99b479d4c24e5eeca10de99032ebd343ef8f` (`L` below = `https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f`)
- ggml `d4716378882593333721eb33f153144b6885caf2` for `docs/gguf.md` (`G` below = `https://github.com/ggml-org/ggml/blob/d4716378882593333721eb33f153144b6885caf2`)
- Hugging Face repos, fetched read-only on 2026-09-02
- Local header dump of `~/models/gguf/nvidia/NVIDIA-Nemotron3-Nano-4B-Q4_K_M.gguf` (header only)

## Question

Which GGUF header fields reliably separate an instruct/chat causal LM from embedding, rerank, vision-projector (mmproj), and base-pretrained models, so that `qit-runtime`'s scan can offer **Generate** (a `/v1/chat/completions` smoke test through `llama-server`) only on artifacts that can actually answer it? What does `llama-server` itself key on?

## Summary

1. `llama-server` does **not** gate `/v1/chat/completions` on model kind. It gates only the embeddings and rerank endpoints, and only on CLI flags (`--embeddings`, `--reranking`), not on header metadata. A missing chat template silently falls back to ChatML. `qit-runtime` therefore has to classify on its own.
2. The header carries strong negative signals that are written deterministically by the converter and read by the loader: `general.type == "mmproj"` / `general.architecture == "clip"` (vision projector), `<arch>.pooling_type` (embedding; value `4` = rerank), `<arch>.attention.causal == false` (encoder-only), `<arch>.classifier.output_labels` (classifier/reranker).
3. `tokenizer.chat_template` is the only positive signal for "instruct". It is written whenever the HF `tokenizer_config.json` (or `chat_template.jinja`/`.json`) has one. Some base checkpoints (Qwen) ship a chat template, so it over-approximates; some old or hand-converted instruct GGUFs lack one, so it under-approximates. Both misclassifications are safe in the sense that llama-server still runs; the base case is the one that produces poor output.
4. `general.finetune`, `general.tags`, `general.base_model.*`, and filename suffixes are heuristics derived from the HF model card and directory name. They are absent whenever the converter was run without a README (the local Nemotron file has none of them). Use them as display hints or tie-breakers, not as gates.
5. Nemotron 3 Nano 4B (`nemotron_h`) carries `general.type=model`, a 10,504-char `tokenizer.chat_template`, no pooling/causal/classifier/clip keys, and no finetune/tags/base_model metadata. It classifies as **instruct** under the header rule and would be missed by every filename heuristic.

## Findings

### F1. What the GGUF spec standardizes

- `general.architecture` is the only required general key ([G/docs/gguf.md#L361-L375](https://github.com/ggml-org/ggml/blob/d4716378882593333721eb33f153144b6885caf2/docs/gguf.md#L361-L375)). Unknown keys must be tolerated and treated as "unknown, default or error as appropriate".
- `general.name`, `general.basename`, `general.finetune` ("What has the base model been optimized toward"), `general.size_label`, `general.tags` are optional general metadata ([G/docs/gguf.md#L386-L407](https://github.com/ggml-org/ggml/blob/d4716378882593333721eb33f153144b6885caf2/docs/gguf.md#L386-L407)); `general.base_model.{count,{id}.name,...}` are optional parent-model pointers ([G/docs/gguf.md#L437-L445](https://github.com/ggml-org/ggml/blob/d4716378882593333721eb33f153144b6885caf2/docs/gguf.md#L437-L445)).
- `tokenizer.chat_template: string` is documented as "a Jinja template that specifies the input format expected by the model" ([G/docs/gguf.md#L710](https://github.com/ggml-org/ggml/blob/d4716378882593333721eb33f153144b6885caf2/docs/gguf.md#L710)).
- `general.type` is **not** in the spec. It exists only in gguf-py (`Keys.General.TYPE = "general.type"`, [L/gguf-py/gguf/constants.py#L23](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/gguf-py/gguf/constants.py#L23)) and in llama.cpp's key table (`LLM_KV_GENERAL_TYPE`, [L/src/llama-arch.cpp#L161](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/src/llama-arch.cpp#L161)). Values are `model`, `adapter`, `imatrix`, `mmproj` ([L/gguf-py/gguf/constants.py#L472-L476](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/gguf-py/gguf/constants.py#L472-L476)).
- The filename convention is `[<Sidecar>]<BaseName><SizeLabel><FineTune><Version><Encoding><Type><Shard>.gguf`; `mmproj` is a defined sidecar prefix, `FineTune` is "e.g. Chat, Instruct" and is explicitly "not intended to be perfectly parsable in the field" ([G/docs/gguf.md#L22-L48](https://github.com/ggml-org/ggml/blob/d4716378882593333721eb33f153144b6885caf2/docs/gguf.md#L22-L48)).

### F2. What the HF converter writes, per model class

The converter is now the `conversion/` package driven by `convert_hf_to_gguf.py` ([L/convert_hf_to_gguf.py#L18-L19](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/convert_hf_to_gguf.py#L18-L19)).

**`general.type`.** Every text model writes `general.type = "model"` via `ModelBase.set_type` ([L/conversion/base.py#L1030-L1031](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/conversion/base.py#L1030-L1031)), called unconditionally from `prepare_metadata` ([L/conversion/base.py#L1057](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/conversion/base.py#L1057)). `MmprojModel` overrides it to `"mmproj"` ([L/conversion/base.py#L2494-L2495](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/conversion/base.py#L2494-L2495)) and its `general.architecture` is the dummy `"clip"` (`MODEL_ARCH.MMPROJ -> "clip"`, [L/gguf-py/gguf/constants.py#L1229](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/gguf-py/gguf/constants.py#L1229); `model_arch = gguf.MODEL_ARCH.MMPROJ`, [L/conversion/base.py#L2390-L2392](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/conversion/base.py#L2390-L2392)). Projectors also write `clip.has_vision_encoder` ([L/conversion/base.py#L2512](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/conversion/base.py#L2512)), `clip.projector_type`, etc. ([L/gguf-py/gguf/constants.py#L362-L367](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/gguf-py/gguf/constants.py#L362-L367)); these are the keys `tools/mtmd/clip.cpp` reads ([L/tools/mtmd/clip-impl.h#L33-L36](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/tools/mtmd/clip-impl.h#L33-L36)). Note that `general.type` is a gguf-py convention, so GGUFs produced by other tools may omit it; `general.architecture == "clip"` and `clip.*` keys are the redundant fallback.

**Encoder-only / embedding archs.** `BertModel.set_gguf_parameters` writes `<arch>.attention.causal = false`, calls `_try_set_pooling_type()`, and writes `<arch>.classifier.output_labels` when the checkpoint has a classification head ([L/conversion/bert.py#L34-L38](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/conversion/bert.py#L34-L38)). `DistilBert`, `Roberta`, `NomicBert`, `NeoBert`, `XLMRoberta`, `JinaBertV2`, `ModernBert` subclass it; `EuroBert` does the same independently ([L/conversion/bert.py#L440-L455](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/conversion/bert.py#L440-L455)). Generic `TextModel` also writes `attention.causal = false` whenever HF `config.json` has `is_causal: false` ([L/conversion/base.py#L1295-L1297](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/conversion/base.py#L1295-L1297)).

**`<arch>.pooling_type`.** `_try_set_pooling_type` reads sentence-transformers `modules.json` + `1_Pooling/config.json` and writes `MEAN`/`CLS`/`LAST` (1/2/3); it writes nothing when there is no pooling module ([L/conversion/base.py#L2121-L2153](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/conversion/base.py#L2121-L2153); enum at [L/gguf-py/gguf/constants.py#L5470-L5475](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/gguf-py/gguf/constants.py#L5470-L5475)). Crucially it is also called for **decoder** archs used as embedders: `Qwen2Model.set_gguf_parameters` (which `Qwen3Model` inherits) ([L/conversion/qwen.py#L66-L68](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/conversion/qwen.py#L66-L68)) and `EmbeddingGemma` ([L/conversion/gemma.py#L185-L186](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/conversion/gemma.py#L185-L186), [#L255](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/conversion/gemma.py#L255)). So a Qwen3-Embedding GGUF has `general.architecture = qwen3`, a chat template, **and** `qwen3.pooling_type`: architecture alone cannot separate it from Qwen3-Instruct; `pooling_type` can.

**Rerank.** `Qwen3Model` detects rerankers from the README title, directory/`_name_or_path` hints, or a `*SequenceClassification` HF architecture ([L/conversion/qwen.py#L180-L207](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/conversion/qwen.py#L180-L207)) and then writes `pooling_type = RANK` (4), `classifier.output_labels = ["yes","no"]`, and a named template `tokenizer.chat_template.rerank` ([L/conversion/qwen.py#L223-L236](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/conversion/qwen.py#L223-L236)). Named templates are written as `tokenizer.chat_template.<name>` plus a `tokenizer.chat_templates` array; the `default` name (if any) goes to plain `tokenizer.chat_template` ([L/gguf-py/gguf/gguf_writer.py#L1253-L1284](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/gguf-py/gguf/gguf_writer.py#L1253-L1284)). BERT-style cross-encoders get `RANK` via the same `classifier.output_labels` path.

**`tokenizer.chat_template`.** `SpecialVocab` loads it from `tokenizer_config.json["chat_template"]`, falling back to `chat_template.jinja` (+ `additional_chat_templates/*.jinja`) or `chat_template.json` ([L/gguf-py/gguf/vocab.py#L315-L335](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/gguf-py/gguf/vocab.py#L315-L335)) and writes it whenever non-`None` ([L/gguf-py/gguf/vocab.py#L105-L108](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/gguf-py/gguf/vocab.py#L105-L108)). Every `_set_vocab_*` path ends in `special_vocab.add_to_gguf` ([L/conversion/base.py#L1798](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/conversion/base.py#L1798), [#L1849](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/conversion/base.py#L1849), [#L1905](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/conversion/base.py#L1905)). Mistral-format checkpoints get a community template unless `--disable-mistral-community-chat-template` ([L/conversion/base.py#L2285-L2309](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/conversion/base.py#L2285-L2309)); RWKV gets a built-in one ([L/conversion/base.py#L2060-L2067](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/conversion/base.py#L2060-L2067)). The converter therefore copies whatever the upstream repo declares; it does not decide "instruct vs base" itself.

**`general.finetune`, `general.tags`, `general.base_model.*`.** Produced by `gguf.Metadata` heuristics ([L/gguf-py/gguf/metadata.py#L61-L75](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/gguf-py/gguf/metadata.py#L61-L75)):
- `finetune` comes from splitting the model id / directory name on `-` and tagging parts matching `chat|instruct|vision|lora` (case-insensitive, full-match) or any unclassified trailing part ([L/gguf-py/gguf/metadata.py#L316-L322](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/gguf-py/gguf/metadata.py#L316-L322), [#L341-L353](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/gguf-py/gguf/metadata.py#L341-L353)), or from `_name_or_path` in `config.json` ([L/gguf-py/gguf/metadata.py#L563-L570](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/gguf-py/gguf/metadata.py#L563-L570)). Note `it` (Gemma's suffix) is not in the regex.
- `tags` comes from the README front-matter `tags` and `pipeline_tag` ([L/gguf-py/gguf/metadata.py#L555-L556](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/gguf-py/gguf/metadata.py#L555-L556)), so `text-generation` / `feature-extraction` / `sentence-similarity` can appear here when a model card was present.
- `base_model.*` comes from the README `base_model` / `base_models` / `base_model_sources` ([L/gguf-py/gguf/metadata.py#L434-L436](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/gguf-py/gguf/metadata.py#L434-L436)).
- All three are written only when non-`None` ([L/gguf-py/gguf/metadata.py#L644](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/gguf-py/gguf/metadata.py#L644), [#L685](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/gguf-py/gguf/metadata.py#L685), [#L729](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/gguf-py/gguf/metadata.py#L729)). No README and a non-descriptive directory name means none of them exist (see F5).

Those embedding/rerank files are expected to also carry `<arch>.pooling_type` per F2 (converter code path); this was not confirmed by reading their raw headers in this pass.

### F4. What llama.cpp / llama-server key on

**Loader.** `general.architecture` is mapped through `LLM_ARCH_NAMES`; `clip` is a "dummy, only used by llama-quantize" entry ([L/src/llama-arch.cpp#L9](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/src/llama-arch.cpp#L9)) and `llama_model_load` throws `"CLIP cannot be used as main model, use it with --mmproj instead"` ([L/src/llama.cpp#L351-L353](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/src/llama.cpp#L351-L353); hparams loading is skipped for it at [L/src/llama-model.cpp#L1215](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/src/llama-model.cpp#L1215)). `load_hparams` reads `<arch>.attention.causal` (default `true`) and `<arch>.pooling_type` (default `NONE`) as optional keys ([L/src/llama-model.cpp#L1222-L1223](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/src/llama-model.cpp#L1222-L1223); defaults at [L/src/llama-hparams.h#L211](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/src/llama-hparams.h#L211), [#L328](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/src/llama-hparams.h#L328)) and `<arch>.classifier.output_labels` into `n_cls_out` ([L/src/llama-model.cpp#L1365-L1368](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/src/llama-model.cpp#L1365-L1368)). The context inherits `causal_attn` and `pooling_type` from hparams unless overridden by CLI ([L/src/llama-context.cpp#L215-L227](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/src/llama-context.cpp#L215-L227)). `general.type` is in the key table but nothing in `src/` branches on it.

**Graph.** BERT-family graphs create `cls`/`cls_out` heads and no `output` tensor ([L/src/models/bert.cpp#L35-L39](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/src/models/bert.cpp#L35-L39)); a generative graph such as `nemotron_h` sets `res->t_logits` from `output` ([L/src/models/nemotron-h.cpp#L57](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/src/models/nemotron-h.cpp#L57), [#L233-L235](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/src/models/nemotron-h.cpp#L233-L235)). Asking an embedding model for a completion is not rejected at the API boundary; it simply has no logits to sample.

**Chat template lookup.** `llama_model_chat_template(model, name)` looks up `tokenizer.chat_template` or `tokenizer.chat_template.<name>` in the raw KV map and returns `nullptr` when absent (with one hard-coded exception for Mistral-Small-2503) ([L/src/llama-model.cpp#L3053-L3070](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/src/llama-model.cpp#L3053-L3070); key suffix rule at [L/src/llama-arch.cpp#L989-L997](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/src/llama-arch.cpp#L989-L997)).

**Fallback to ChatML.** `common_chat_templates_init` takes the model's template if present, else the CLI override, and if the result is empty (or literally `"chatml"`) substitutes the built-in `CHATML_TEMPLATE_SRC` ([L/common/chat.cpp#L753-L782](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/common/chat.cpp#L753-L782), template at [#L704-L710](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/common/chat.cpp#L704-L710)). `has_explicit_template` records whether it came from the model or the flag ([#L760-L772](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/common/chat.cpp#L760-L772)), but the server only uses it for logging; it never refuses. The legacy non-Jinja path `llama_chat_apply_template` likewise treats a null template as `"chatml"` ([L/src/llama.cpp#L508-L515](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/src/llama.cpp#L508-L515)). The server README states "By default, the ChatML template will be used" ([L/tools/server/README.md#L1312](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/tools/server/README.md#L1312)).

**Server endpoint gating.** Routes are registered unconditionally ([L/tools/server/server.cpp#L257-L277](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/tools/server/server.cpp#L257-L277)). `post_chat_completions` parses the body through the loaded templates and calls `handle_completions_impl` with no model-kind check ([L/tools/server/server-context.cpp#L4903-L4915](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/tools/server/server-context.cpp#L4903-L4915)). The only kind-related refusals are `"This server does not support embeddings. Start it with --embeddings"` ([#L5363-L5367](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/tools/server/server-context.cpp#L5363-L5367)) and `"This server does not support reranking. Start it with --reranking"`, which requires `params.embedding && pooling_type == RANK` ([#L5120-L5125](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/tools/server/server-context.cpp#L5120-L5125)). Both flags are operator input: `--embedding` "restrict to only support embedding use case; use only with dedicated embedding models", `--reranking` sets `embedding = true` and `pooling_type = RANK` ([L/common/arg.cpp#L3490-L3503](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/common/arg.cpp#L3490-L3503); README rows at [L/tools/server/README.md#L212-L213](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/tools/server/README.md#L212-L213)). A grep of `tools/server/*.cpp` at this commit finds no code path that rejects completions when `params.embedding` is set; the older "Start it without `--embeddings`" refusal is gone. `common_init_from_params` only warns when a RANK model lacks BOS/EOS/SEP tokens or a `rerank` template ([L/common/common.cpp#L1483-L1499](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/common/common.cpp#L1483-L1499)).

Net: `llama-server` will happily start a BERT or mmproj-less embedding model and expose `/v1/chat/completions`; it will error at load only for `clip` mmproj files. The decision has to be made by `qit-runtime` before spawning the worker.

## Recommendation for qit-runtime's scan

1. **Classify in `read_gguf_meta`, not at spawn time.** Extend `GgufMeta` with `general_type: Option<String>`, `has_chat_template: bool`, `pooling_type: Option<u32>`, `causal_attn: Option<bool>`, `has_classifier_labels: bool`, `has_clip_keys: bool`, `finetune: Option<String>`, and a derived `kind: ArtifactKind` (`Instruct | Base | Embedding | Rerank | VisionProjector | Unknown`) computed by the table above. Persist `kind` on the artifact row so the UI and the smoke-test endpoint read the same value.
2. **Reader changes needed.** The current reader records every key but discards value types 7 (bool) and arrays as `Other`. Add a `Bool` variant so `<arch>.attention.causal` is readable, and keep the existing "key present" semantics for `clip.*`, `classifier.output_labels`, and `tokenizer.chat_template.rerank` (presence is enough; the values are not needed). `tokenizer.chat_template` already parses as `Str` (10 KB on Nemotron, well under the 1 MiB cap); only its non-emptiness needs storing. `pooling_type` and `general.type` already parse with the existing `Uint`/`Str` paths.
3. **Gate Generate on `kind == Instruct`.** Return `409`/`422` from the smoke-test route for any other kind with the kind in the error body, and let the UI disable the button with the reason. Offer a per-artifact user override (persisted like a pin) for rows 6/7 misclassifications; do not offer overrides for rows 1-4.
4. **Do not rely on llama-server to refuse.** It exposes `/v1/chat/completions` regardless of model kind and only errors at load for `clip` files (F4). Spawning an embedding model and letting the request fail wastes a session and a load/unload cycle.
5. **Filename heuristics are display-only.** Nemotron proves a real instruct artifact can carry no name marker and no `general.finetune` (F5); Qwen proves a base checkpoint can carry a chat template (F3). Neither signal should be a hard gate.
6. **Hybrid-arch follow-up (out of scope for #13).** `head_count_kv` and `feed_forward_length` are per-layer arrays on `nemotron_h`; the reader's scalar `u32_at` returns `None` for them, so KV estimates for hybrid models need an array-aware path.
