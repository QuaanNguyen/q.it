# Peak RSS of a child worker on macOS

Research for [#11](https://github.com/QuaanNguyen/q.it/issues/11) (part of [#8](https://github.com/QuaanNguyen/q.it/issues/8); unblocks the peak-RSS item on [#7](https://github.com/QuaanNguyen/q.it/issues/7)).

Environment inspected: macOS 26.6.2 (25G83), Apple Silicon, Command Line Tools SDK `MacOSX.sdk` (26.5). Kernel sources are cited from `apple-oss-distributions/xnu` at commit `f6217f8`; `ps` from `apple-oss-distributions/adv_cmds` at `6bed873`; llama.cpp at `b81c99b`; Rust `libc` at `96b7867`; `libproc` crate at `43a5f19` (v0.14.11).

## Question

How should `qit-runtime` (Rust parent) measure a `llama-server` child's peak resident memory on macOS? Compare (a) sampling `proc_pidinfo(PROC_PIDTASKINFO)` / `proc_pid_rusage(RUSAGE_INFO_V*)`, (b) `ru_maxrss` from `wait4`/`getrusage` at exit, (c) shelling out to `ps -o rss=`. For each: what it measures, peak vs current, privilege requirements, polling cost. Critically: with `-ngl 999` on Metal, are the model weights (unified memory, Metal shared buffers) counted in resident size, phys_footprint, or neither? Does `ri_lifetime_max_phys_footprint` give a peak without polling?

## Summary of findings

| Metric | Kernel source of truth | Peak or current | Privilege | Cost |
|---|---|---|---|---|
| `pti_resident_size` (`PROC_PIDTASKINFO`) | `phys_mem` ledger balance | current | same uid (or root) | ~0.5 us/call |
| `ri_resident_size` (`RUSAGE_INFO_V0+`) | `phys_mem` ledger balance | current | same uid (or root) | ~0.5 us/call |
| `ri_phys_footprint` (`RUSAGE_INFO_V0+`) | `phys_footprint` ledger balance | current; zeroed on zombie | same uid (or root) | ~0.5 us/call |
| `ri_lifetime_max_phys_footprint` (`RUSAGE_INFO_V4+`) | `phys_footprint` ledger lifetime max | peak, no polling; survives into zombie | same uid (or root) | ~0.5 us/call |
| `ru_maxrss` (`wait4`, `getrusage`) | `phys_mem` ledger lifetime max, **bytes** | peak, no polling; delivered at reap | own child only | free (one call at exit) |
| `ps -o rss=` | `task_info(TASK_BASIC_INFO).resident_size / 1024` | current, KiB | works because `/bin/ps` is entitled | ~2 ms fork+exec per sample |

Two different quantities are in play, and they diverge exactly on the mmap'd model weights:

- **Resident size** (`phys_mem` ledger): every physical page mapped into the process pmap, file-backed or anonymous. This is what `ps rss`, `pti_resident_size`, `ri_resident_size`, and `ru_maxrss` report.
- **Physical footprint** (`phys_footprint` ledger): dirty/anonymous memory plus IOKit mappings; clean file-backed pages are excluded by definition. This is what Activity Monitor and `top` show, and what `ri_phys_footprint` / `ri_lifetime_max_phys_footprint` report.

## Findings

### 1. What each API reads in the kernel

All three sampling APIs collapse onto two per-task ledgers.

`proc_pidinfo(PROC_PIDTASKINFO)` fills `struct proc_taskinfo` whose `pti_resident_size` is documented as "resident memory size (bytes)" ([`sys/proc_info.h` L124-126, SDK](file:///Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/include/sys/proc_info.h); flavor constant `PROC_PIDTASKINFO = 4` at L726). The kernel path is `proc_pidtaskinfo()` → `fill_taskprocinfo()`, which does `ledger_get_balance(task->ledger, task_ledgers.phys_mem, &ptinfo->pti_resident_size)` ([bsd/kern/proc_info.c L918-928](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/proc_info.c#L918-L928); [osfmk/kern/bsd_kern.c L1080-1081](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/kern/bsd_kern.c#L1080-L1081)).

`proc_pid_rusage(pid, RUSAGE_INFO_Vn, buf)` fills `struct rusage_info_vN` ([`sys/resource.h` L186-193 flavors, L202-420 structs, SDK](file:///Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/include/sys/resource.h)). `RUSAGE_INFO_CURRENT` is V6 on this SDK. The kernel path is `gather_rusage_info()` → `fill_task_rusage()`:

- `ri_resident_size` = `ledger_get_balance(phys_mem)` (same ledger as `pti_resident_size`).
- `ri_phys_footprint` = `get_task_phys_footprint()` = `phys_footprint` ledger balance.
- `ri_wired_size` = `get_task_wired_mem()`.

([osfmk/kern/bsd_kern.c L1274-1277](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/kern/bsd_kern.c#L1274-L1277), [L540-543](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/kern/bsd_kern.c#L540-L543)). `RUSAGE_INFO_V4` and later add `ri_lifetime_max_phys_footprint = get_task_phys_footprint_lifetime_max()` = `ledger_get_lifetime_max(phys_footprint)` ([bsd/kern/kern_resource.c L3372-3374](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/kern_resource.c#L3372-L3374); [osfmk/kern/bsd_kern.c L569-581](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/kern/bsd_kern.c#L569-L581)). The kernel tracks lifetime maxima for both `phys_footprint` and `phys_mem` via `ledger_track_maximum()` ([osfmk/kern/task.c L1462-1463](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/kern/task.c#L1462-L1463)).

No `proc_pidinfo` or `proc_pid_rusage` flavor exposes the lifetime max of `phys_mem` (peak resident) while the process is alive. That value exists only as `MACH_TASK_BASIC_INFO.resident_size_max` via `task_info()` on a task port ([osfmk/kern/task.c L5519-5520](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/kern/task.c#L5519-L5520); [osfmk/mach/task_info.h L327-342](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/mach/task_info.h#L327-L342)), and as `ru_maxrss` at exit (next section).

`libproc.h` carries a caveat: "This header file contains private interfaces to obtain process information. These interfaces are subject to change in future releases." ([`libproc.h` L41-44, SDK](file:///Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/include/libproc.h)). Both `proc_pidinfo` (available since 10.5) and `proc_pid_rusage` (since 10.9) are nevertheless declared with public availability macros (L96, L111) and are what `ps`, `top`, and Activity Monitor build on.

### 2. `ru_maxrss` from `wait4` / `getrusage`: peak resident, in bytes

`man 2 getrusage` on this Mac: "`ru_maxrss` the maximum resident set size utilized (in bytes)." The SDK header marks it `long ru_maxrss; /* max resident set size (PL) */` ([`sys/resource.h` L163](file:///Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/include/sys/resource.h)). This differs from Linux (kilobytes).

Kernel derivation: `calcru()` sets `p->p_stats->p_ru.ru_maxrss = (long)tinfo.resident_size_max` from `task_info(MACH_TASK_BASIC_INFO)` ([bsd/kern/kern_resource.c L1766-1790](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/kern_resource.c#L1766-L1790)), and `resident_size_max` is `ledger_get_lifetime_max(task->ledger, task_ledgers.phys_mem, ...)` ([osfmk/kern/task.c L5520](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/kern/task.c#L5520)). So `ru_maxrss` is the exact lifetime peak of the same `phys_mem` ledger that `ps rss` / `pti_resident_size` sample, with no sampling gap.

At exit, `proc_exit()` runs `calcru()` and copies `p_stats->p_ru` into the zombie record `p->p_ru->ru`, then `ruadd()`s the process's own reaped children ([bsd/kern/kern_exit.c L2500-2511](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/kern_exit.c#L2500-L2511)). `wait4()` copies `p->p_ru->ru` to the caller's `rusage` pointer ([kern_exit.c L2979-2995](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/kern_exit.c#L2979-L2995)). `ruadd()` takes the **max** of `ru_maxrss` rather than summing ([kern_resource.c L1848-1863](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/kern_resource.c#L1848-L1863)). `llama-server` spawns no children, so `wait4` returns exactly its peak.

`getrusage(RUSAGE_CHILDREN)` returns `p_stats->p_cru`, the `ruadd()` accumulation over **all** reaped children ([kern_resource.c L1825-1830](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/kern_resource.c#L1825-L1830)). Since `ruadd` keeps the max, it cannot attribute a peak to a specific worker once more than one has been reaped. `man 2 getrusage` BUGS: "There is no way to obtain information about a child process that has not yet terminated." Use `wait4(pid, ...)` per child, not `RUSAGE_CHILDREN`.

Privilege: `wait4` only works on your own children; no entitlement.

Empirical check on this Mac (Python child that allocated 200 MiB then exited): `wait4` returned `ru_maxrss = 225001472` = 214.6 MiB, matching `ri_resident_size = 214.6 MiB` sampled while alive. `getrusage(RUSAGE_SELF).ru_maxrss` for the probe process itself was 19,070,976 while its resident size was 17,874,944, so the value is unambiguously bytes.

### 3. Zombie window: `proc_pid_rusage` works after exit, before reap

`libproc.h`: `proc_pid_rusage` returns usage "for the given pid, which can be a live process or a zombie" (L106-111). In `proc_prepareexit()`, before the task is torn down (`task_terminate_internal` follows at [kern_exit.c L1633-1636](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/kern_exit.c#L1633-L1636)), the kernel stashes `gather_rusage_info(p, &rup->ri, RUSAGE_INFO_CURRENT)` and then explicitly sets `rup->ri.ri_phys_footprint = 0` ([kern_exit.c L2070-2087](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/kern_exit.c#L2070-L2087)). `proc_get_rusage()` returns this stashed copy for zombies ([kern_resource.c L3456-3466](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/kern_resource.c#L3456-L3466)).

Consequences, confirmed empirically here: on the zombie, `ri_resident_size` was the exit-time value (213.2 MiB), `ri_phys_footprint` was 0, `ri_lifetime_max_phys_footprint` was preserved (206.8 MiB), and after `wait4` reaped it, `proc_pid_rusage` returned `-1`/`ESRCH`. So a parent can read `ri_lifetime_max_phys_footprint` after exit but must do so **before** reaping, and must not use zombie `ri_phys_footprint`.

### 4. Privilege model for `proc_pidinfo` / `proc_pid_rusage`

Both go through `proc_security_policy(..., CHECK_SAME_USER)`: if the caller's uid differs from the target's, the call fails with `EPERM` unless the caller holds `PRIV_GLOBAL_PROC_INFO` (root by default) ([bsd/kern/proc_info.c L3161-3203](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/proc_info.c#L3161-L3203); `PROC_PIDTASKINFO` uses `CHECK_SAME_USER` by default at [L2200-2213](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/proc_info.c#L2200-L2213); `proc_pid_rusage` at [L3820-3848](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/proc_info.c#L3820-L3848)). No entitlement is needed for a same-uid child. No task port is involved, so hardened-runtime restrictions on `task_for_pid` do not apply.

### 5. Cost of polling

Each `proc_pidinfo(PROC_PIDTASKINFO)` or `proc_pid_rusage(RUSAGE_INFO_V4)` is one syscall that reads a ledger balance; measured here at 0.5-0.6 us per call (20,000 iterations, Python ctypes, so an upper bound). At a 100 ms sampling interval that is about 5 us of CPU per second, negligible against a smoke test.

`ps -o rss= -p <pid>` measured at ~2.1 ms per invocation (fork+exec+`task_read_for_pid`+parse), 3-4 orders of magnitude more expensive per sample, and it also produces an inherited-fd/zombie-race surface the supervisor does not need.

### 6. What `ps -o rss` actually reports, and why it works

Apple's `ps` gets a task port via `task_read_for_pid()` and calls `task_info(TASK_BASIC_INFO)` ([adv_cmds ps/tasks.c L90-115](https://github.com/apple-oss-distributions/adv_cmds/blob/6bed8737a34dbb54782a18f47dccf933a9967a12/ps/tasks.c#L90-L115)); `rss` prints `tasks_info.resident_size / 1024` ([ps/print.c L785-794](https://github.com/apple-oss-distributions/adv_cmds/blob/6bed8737a34dbb54782a18f47dccf933a9967a12/ps/print.c#L785-L794)). `man 1 ps`: "rss the real memory (resident set) size of the process (in 1024 byte units)". In the kernel, `TASK_BASIC_INFO` is the `phys_mem` ledger balance ([osfmk/kern/task.c L5417-5453](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/kern/task.c#L5417-L5453)). So `ps rss` == `pti_resident_size` == `ri_resident_size`, rounded down to KiB. Verified: `ps` printed `17456` KiB while `pti_resident_size` was 17,874,944 bytes (= 17456 × 1024).

The `rss` keyword is flagged `ENTITLED` in Apple's build ([ps/keyword.c L171-175](https://github.com/apple-oss-distributions/adv_cmds/blob/6bed8737a34dbb54782a18f47dccf933a9967a12/ps/keyword.c#L171-L175)), and `codesign -d --entitlements - /bin/ps` on this Mac shows `com.apple.system-task-ports.read`. That is a private entitlement; `qit-runtime` cannot take the same `task_read_for_pid` route, which also rules out reading `MACH_TASK_BASIC_INFO.resident_size_max` live. It only reports current, not peak.

### 7. Are Metal-resident weights counted?

How `llama-server` maps weights on Apple Silicon (source, not observation):

- Default load mode is `auto`, which uses `mmap` unless a backend lacks `mmap_support` ([common/common.h L484](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/common/common.h#L484); [common/arg.cpp L2713-2720](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/common/arg.cpp#L2713-L2720); [src/llama-model.cpp L1400-1411](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/src/llama-model.cpp#L1400-L1411)). The Metal backend advertises `mmap_support = true` and `buffer_from_host_ptr = true` ([ggml/src/ggml-metal/ggml-metal.cpp L689-694](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/ggml/src/ggml-metal/ggml-metal.cpp#L689-L694)).
- The file is mapped `mmap(NULL, size, PROT_READ, MAP_SHARED, fd, 0)` ([src/llama-mmap.cpp L471-481](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/src/llama-mmap.cpp#L471-L481)), i.e. clean, file-backed, read-only pages.
- Weight tensors are then handed to Metal via `ggml_backend_dev_buffer_from_host_ptr` ([src/llama-model.cpp L1717-1745](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/src/llama-model.cpp#L1717-L1745)) → `ggml_metal_buffer_map` → `[device newBufferWithBytesNoCopy:ptr length:size options:MTLResourceStorageModeShared deallocator:nil]` over the mmap'd range ([ggml/src/ggml-metal/ggml-metal-device.m L2150-2174](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/ggml/src/ggml-metal/ggml-metal-device.m#L2150-L2174)). KV cache and compute buffers are also `MTLResourceStorageModeShared` no-copy wrappers, but over host-allocated anonymous memory ([ggml-metal-device.m L2099-2110](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/ggml/src/ggml-metal/ggml-metal-device.m#L2099-L2110)), chosen because `hasUnifiedMemory` is true ([L1119, L1251](https://github.com/ggml-org/llama.cpp/blob/b81c99b479d4c24e5eeca10de99032ebd343ef8f/ggml/src/ggml-metal/ggml-metal-device.m#L1251)).

Apple's documentation for these Metal APIs: `MTLStorageMode.shared` means "The CPU and GPU share access to the resource, allocated in system memory" and is the default for buffers on Apple silicon ([developer.apple.com: MTLStorageMode.shared](https://developer.apple.com/documentation/metal/mtlstoragemode/shared)); `makeBuffer(bytesNoCopy:...)` "Creates a buffer that wraps an existing contiguous memory allocation" that "needs to exist within a single virtual memory (VM) region" ([developer.apple.com: makeBuffer(bytesNoCopy:length:options:deallocator:)](https://developer.apple.com/documentation/metal/mtldevice/makebuffer(bytesnocopy:length:options:deallocator:))); Apple GPUs "have a unified memory model in which the CPU and the GPU share system memory" ([Choosing a resource storage mode for Apple GPUs](https://developer.apple.com/documentation/metal/choosing-a-resource-storage-mode-for-apple-gpus)). There is no separate VRAM copy: the weights are the process's own mmap'd pages.

**Resident size (`phys_mem`): yes, counted.** On arm64 the pmap credits `phys_mem` for every new valid user mapping regardless of backing, then additionally credits `internal` (+`phys_footprint`) for anonymous pages or `external` for file-backed pages ([osfmk/arm/pmap/pmap.c L6541-6585](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/arm/pmap/pmap.c#L6541-L6585)). Once the weight pages are faulted in (by llama.cpp's prefetch/`posix_madvise`, CPU reads during load, or the driver wiring them for the GPU), they are in the CPU pmap and therefore in `phys_mem`. This is consistent with the observation in #11: a 2.84 GB Q4_K_M model showed ~3.14 GB `ps rss` while loaded (weights + ~300 MB of KV cache, compute buffers, dyld shared cache pages and heap).

**Physical footprint (`phys_footprint`): not by the mmap itself; possibly via the GPU driver.** The ledger definition is "phys_footprint = (internal - alternate_accounting) + (internal_compressed - alternate_accounting_compressed) + iokit_mapped + purgeable_nonvolatile + purgeable_nonvolatile_compressed + page_table" ([osfmk/kern/task.c L1222-1256](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/kern/task.c#L1222-L1256)). Clean file-backed pages are `external`, which is not a term of that sum, so the mmap'd GGUF pages are excluded from footprint as plain CPU mappings. `man 1 footprint` states the same from the user side: footprint is "Dirty" memory, "Clean ... file-backed memory" is "deliberately excluded", and "resident size includes clean and volatile purgeable memory that can be reclaimed by the kernel". However, the footprint ledger also gets a credit of `bytes` to both `iokit_mapped` and `phys_footprint` whenever an IOKit memory descriptor is mapped into the task ([osfmk/vm/vm_map.c L22253-22259](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/vm/vm_map.c#L22253-L22259)), and `man 1 footprint` says the ledger "includes values from multiple sub-ledgers, such as network memory, graphics memory" (categories like "IOKit (graphics)") and that GPU-shared memory is wired: "when a process uses the GPU, the driver places graphics textures into memory and then shares that memory with the GPU". Whether the closed-source AGX driver charges a no-copy `MTLBuffer` over a file mapping to `iokit_mapped` (and so to `phys_footprint`) is not determinable from public sources. Treat `phys_footprint` as **undetermined for the weights** until measured (see follow-up below).

**`ri_lifetime_max_phys_footprint` gives a peak without polling**, but it is a peak of `phys_footprint`, so for the weights it inherits the same undetermined status. On this SDK `RUSAGE_INFO_CURRENT` is V6; V4 is the lowest flavor carrying the field. The kernel gathers `RUSAGE_INFO_CURRENT` at exit regardless of which flavor the reader later requests ([kern_exit.c L2079](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/kern_exit.c#L2079)).

**Which number does the planner want?** `CONTEXT.md` defines the stable budget as unified memory minus OS reserve, capped by Metal `recommendedMaxWorkingSetSize`, and an artifact's fit is judged by "estimated bytes" against headroom. The weights occupy unified memory whether or not the footprint ledger bills them, and `recommendedMaxWorkingSetSize` is "how much memory ... this GPU device can allocate" ([developer.apple.com](https://developer.apple.com/documentation/metal/mtldevice/recommendedmaxworkingsetsize)). The metric that demonstrably includes the weights is resident size. Its known weakness is the mirror of footprint's strength: it also counts clean, reclaimable pages (shared cache, any read-only file mapping), which slightly overstates pressure. For a worker whose dominant term is the model file, that overstatement is small and in the safe direction.

### 8. Rust bindings

- `libc` (macOS target) declares `proc_pidinfo`, `proc_pid_rusage`, `proc_taskinfo` (with `pti_resident_size: u64`), `rusage_info_v4` (with `ri_lifetime_max_phys_footprint: u64`), `PROC_PIDTASKINFO`, `RUSAGE_INFO_V4`, `wait4`, and `getrusage` ([src/unix/bsd/apple/mod.rs L567-569, L1031-1061, L3627, L3895, L5051-5057, L5082](https://github.com/rust-lang/libc/blob/96b78673b6e396ee68c5161798faf0df11623290/src/unix/bsd/apple/mod.rs#L1031-L1061); [src/unix/bsd/mod.rs L799-804 `wait4`](https://github.com/rust-lang/libc/blob/96b78673b6e396ee68c5161798faf0df11623290/src/unix/bsd/mod.rs#L799-L804); [src/unix/mod.rs L1365 `getrusage`](https://github.com/rust-lang/libc/blob/96b78673b6e396ee68c5161798faf0df11623290/src/unix/mod.rs#L1365)). `rusage_info_v5`/`v6` are not in `libc` at this commit; V4 has every field this ticket needs.
- `libproc` crate v0.14.11 wraps these as `pidinfo::<TaskInfo>(pid, 0)` and `pidrusage::<RUsageInfoV4>(pid)` ([src/libproc/proc_pid.rs L304](https://github.com/andrewdavidmackenzie/libproc-rs/blob/43a5f19c3d6620537bf3a28a5f9c73ae5c7d644f/src/libproc/proc_pid.rs#L304); [src/libproc/pid_rusage.rs L24-35, L270-330, L383-400](https://github.com/andrewdavidmackenzie/libproc-rs/blob/43a5f19c3d6620537bf3a28a5f9c73ae5c7d644f/src/libproc/pid_rusage.rs#L383-L400); [src/libproc/task_info.rs L5-12](https://github.com/andrewdavidmackenzie/libproc-rs/blob/43a5f19c3d6620537bf3a28a5f9c73ae5c7d644f/src/libproc/task_info.rs#L5-L12)). It returns `Err(String)` and pulls in bindgen-generated types; two `unsafe` calls through `libc` are smaller for this use.
- `std::process::Child::wait()`/`try_wait()` call `waitpid` and discard rusage. To get `ru_maxrss` the supervisor must reap with `libc::wait4(child.id() as pid_t, &mut status, 0, &mut rusage)` itself and then not call `Child::wait()` (it would return `ECHILD`, which `std` tolerates, but the status must come from `wait4`). `supervisor.rs` currently reaps via `try_wait()` in `reap()` and `kill_child()`, so those two sites are where the change goes.

## Recommendation for qit-runtime

**Primary metric: peak resident size in bytes, from `ru_maxrss` returned by `wait4` when the worker exits.** It is the kernel's own lifetime maximum of the same `phys_mem` ledger that `ps rss` reads, it needs no polling, no entitlement, and it is the one metric shown to include Metal-mapped weights (Finding 7). Units are bytes on macOS; do not divide by 1024.

**Live metric during the smoke test: sample `proc_pid_rusage(pid, RUSAGE_INFO_V4)` every 250 ms** and keep a running max of `ri_resident_size` (and record `ri_phys_footprint` and `ri_lifetime_max_phys_footprint` alongside). One call per sample costs ~0.5 us and returns resident, footprint, and footprint-peak together, so prefer it over `PROC_PIDTASKINFO` (resident only). A 250 ms interval will miss sub-250 ms spikes; the `wait4` value at exit closes that gap for the final record.

**Exit strategy:**

1. On worker exit (normal or after `kill`), call `proc_pid_rusage(pid, RUSAGE_INFO_V4)` on the zombie and save `ri_lifetime_max_phys_footprint` (ignore zombie `ri_phys_footprint`, it is zeroed).
2. Then reap with `libc::wait4(pid, &mut status, 0, &mut rusage)` and save `rusage.ru_maxrss` as `peak_resident_bytes`.
3. Persist both: `peak_resident_bytes` (planner-facing, compare against the artifact estimate) and `peak_footprint_bytes` (diagnostic, to be compared with resident once the follow-up below has run).
4. Never use `getrusage(RUSAGE_CHILDREN)`; it collapses to a max across all reaped workers.
5. Do not shell out to `ps`; it is ~2 ms per sample, current-only, and only works because `/bin/ps` is entitled to read task ports.

**Correctness notes for the implementation:**

- `ru_maxrss` is `long` (i64) bytes; `ri_*` are `u64` bytes; `pti_resident_size` is `u64` bytes.
- If the sampler races the exit and the pid is already reaped, `proc_pid_rusage` returns `ESRCH`; treat as "no sample".
- The same-uid check means this works for the daemon's own children without root; it would fail if a future design ran workers under a different user.

**Follow-up experiment (out of scope for this ticket, cheap to run):** with a loaded worker, run `footprint -p <pid>` and `vmmap --summary <pid>` and compare against `ri_resident_size` / `ri_phys_footprint`. If the "IOKit (graphics)" or wired categories account for the GGUF pages, `phys_footprint` also includes the weights and the two peaks should agree within the clean-shared-cache delta; if `phys_footprint` is roughly `resident - model_bytes`, then footprint excludes mmap'd weights and `peak_resident_bytes` must stay primary. Either way the recording strategy above does not change, only the interpretation of `peak_footprint_bytes`.
